# 00. INSTRUCTIONS POUR L'AGENT DE DÉVELOPPEMENT

> **Lis intégralement ce document avant d'écrire la moindre ligne de code.**

## 00.1 Ta mission

Tu dois construire **l'intégralité** de la plateforme INFOSPRO.NET décrite ci-dessous : base de données, backend serverless, API, site public (front-office), tableau de bord d'administration (back-office), moteur SEO, régie publicitaire, module newsletter, et toute l'infrastructure associée.

Ce document est **normatif**. Chaque section contient des spécifications directement implémentables : schéma SQL, routes d'API, arborescence de fichiers, jetons de design, noms de composants, règles métier, critères d'acceptation.

## 00.2 Règles absolues

1. **Ne simplifie rien.** Si une fonctionnalité est décrite, elle doit être implémentée entièrement, pas en version « démo ».
2. **Aucune donnée en dur.** Tout texte affiché sur le site public doit provenir de la base de données ou de la table `translations`. Aucun titre de rubrique, aucun libellé de menu, aucune adresse e-mail, aucun lien social ne doit être écrit dans le code.
3. **Respecte les noms.** Les noms de tables, colonnes, routes, composants et variables d'environnement donnés ici sont contractuels. Ne les renomme pas.
4. **TypeScript strict.** `strict: true`, aucun `any` implicite, aucun `@ts-ignore` sans commentaire justificatif.
5. **Pas de `localStorage` pour des données métier.** Uniquement pour les préférences d'affichage (thème, mode données réduites).
6. **Sécurité côté serveur.** Chaque vérification de permission se fait sur le serveur. Masquer un bouton n'est jamais une protection.
7. **Mobile d'abord.** Toute interface est conçue d'abord pour un écran de 360 px, puis élargie.
8. **Performance dès le premier commit.** Ne code pas « on optimisera après ». Les budgets de la section 16 sont bloquants.
9. **Si une information manque**, choisis l'option la plus proche de ce qui se fait sur BBC News, The Economist ou Le Monde, et documente ton choix dans `/docs/DECISIONS.md`.
10. **Langue du produit :** français. Langue du code (variables, fonctions) : anglais. Commentaires : français.

## 00.3 Ordre d'exécution imposé

Construis dans cet ordre. Ne passe à la phase suivante qu'une fois la précédente fonctionnelle et testée.

```
PHASE 1  Socle          → repo, config, DB, migrations, seed, auth, RBAC
PHASE 2  Back-office    → CRUD articles, éditeur blocs, médiathèque, taxonomies
PHASE 3  API publique   → endpoints de lecture, cache, recherche
PHASE 4  Front-office   → design system, layouts, pages, animations
PHASE 5  Modules        → flash, à la une, direct, météo, reportages
PHASE 6  SEO            → socle technique + moteur de mots-clés + assistant
PHASE 7  Monétisation   → régie publicitaire + newsletter
PHASE 8  Finition       → i18n, a11y, perf, tests, observabilité, docs
```

Le détail de chaque phase, avec ses critères d'acceptation, figure en **section 20**.

## 00.4 Identité visuelle imposée

- **Couleurs :** blanc, noir, rouge — strictement. Aucune autre couleur décorative.
- **Rouge de marque :** `#C8102E`
- **Le rouge est un signal, pas une décoration.** Réservé à : marque, liens, statuts d'urgence (direct/flash/alerte), un seul accent par bloc. Maximum 10 % de surface rouge par page.
- **Langage visuel :** presse imprimée haut de gamme — filets fins, typographie serif en titraille, densité maîtrisée. Pas d'ombres portées diffuses, pas de dégradés, pas de coins très arrondis, pas d'esthétique « SaaS ».

# 01. CONTEXTE ET OBJECTIFS

## 01.1 Nature du produit

Site d'information généraliste, national et international, produit depuis la Guinée, avec ambition de qualité comparable aux grands médias mondiaux. Contenus en français au lancement, architecture multilingue native (anglais en phase 2, arabe RTL prévu).

## 01.2 Contraintes structurantes

| Contrainte | Conséquence technique directe |
|---|---|
| Audience majoritairement sur 3G/4G instable, forfaits data coûteux | Budget strict de poids de page, mode données réduites, ISR agressif |
| Parc Android d'entrée de gamme (4 Go RAM) | Animations `transform`/`opacity` uniquement, JS initial < 180 Ko |
| Rédaction non technique | Back-office en français, vocabulaire de presse, formation en 4 h |
| Pics d'audience imprévisibles (élections, crises) | Serverless élastique, cache en périphérie, pas de serveur à dimensionner |
| Extension future (abonnements, annonces, emploi) | Schéma relationnel extensible, pas de refonte nécessaire |
| Lecteurs répartis sur 4 continents | CDN mondial, fuseaux horaires, éditions géographiques |

## 01.3 Objectifs mesurables à 12 mois

| Objectif | Indicateur | Cible |
|---|---|---|
| Audience | Visiteurs uniques mensuels | ≥ 300 000, dont 25 % hors Guinée |
| Fidélisation | Abonnés newsletter actifs | ≥ 20 000 · ouverture ≥ 35 % |
| SEO | Part du trafic organique | ≥ 45 % |
| Performance | Core Web Vitals terrain p75 | LCP < 2,0 s · INP < 200 ms · CLS < 0,1 |
| Disponibilité | Uptime mensuel | ≥ 99,9 % |
| Autonomie | Modifications sans développeur | 100 % du contenu, 95 % de la mise en page |
| Monétisation | Emplacements publicitaires actifs | ≥ 18 formats distincts |
| Productivité | Délai de publication d'une brève | < 3 minutes |

## 01.4 Hors périmètre de cette implémentation

Ces éléments ne sont **pas** à construire maintenant, mais le schéma de données et l'architecture doivent les rendre possibles sans refonte :

- Applications mobiles natives iOS/Android
- Paywall et abonnements payants (prévoir `users.subscription_status`, table `subscriptions` vide)
- Web radio / podcast en flux continu
- Petites annonces et annonces légales

## 02.1 Choix technologiques

| Couche | Technologie | Version | Note |
|---|---|---|---|
| Framework | **Next.js** App Router | 15.x | React Server Components par défaut |
| Langage | **TypeScript** | 5.x | `strict: true` |
| UI | **React** | 19.x | — |
| Styles | **Tailwind CSS** | 4.x | Jetons de design en variables CSS |
| Animations | **Framer Motion** (`motion`) | 11.x+ | + transitions CSS natives pour le simple |
| Base de données | **PostgreSQL** | 16+ | Serverless : Neon, Supabase, ou Aurora Serverless v2 |
| ORM | **Prisma** | 5.x+ | Alternative acceptée : Drizzle |
| Pool de connexions | PgBouncer / pooler intégré | — | **Obligatoire** en serverless |
| Auth | **Auth.js (NextAuth)** v5 | 5.x | Credentials + TOTP 2FA |
| Validation | **Zod** | 3.x | Schémas partagés client/serveur |
| Recherche | **Meilisearch** | 1.x | Repli : PostgreSQL FTS + `pg_trgm` |
| Cache / compteurs | **Redis serverless** (Upstash) | — | Vues, sessions, rate limit |
| Stockage objet | **S3** ou **Cloudflare R2** | — | Médias |
| Transformation images | `next/image` + service de transformation | — | AVIF/WebP, 6 largeurs |
| Vidéo | **Mux** ou **Cloudflare Stream** | — | HLS adaptatif, sous-titres |
| E-mail | **Resend** ou **Amazon SES** | — | SPF/DKIM/DMARC obligatoires |
| Files & cron | **QStash** ou **Inngest** | — | Tâches asynchrones |
| Éditeur riche | **TipTap** | 2.x | Sortie **JSON blocs**, jamais HTML brut |
| Formulaires | **React Hook Form** + Zod | — | — |
| Tables admin | **TanStack Table** | 8.x | — |
| Graphiques | **Recharts** | — | Dashboards |
| Tests unitaires | **Vitest** | — | — |
| Tests E2E | **Playwright** | — | — |
| Erreurs | **Sentry** | — | — |
| Hébergement | **Vercel** | — | Alternative : AWS Lambda + CloudFront |

## 02.2 Architecture en couches

```
┌─────────────────────────────────────────────────────────┐
│  EDGE : CDN mondial, cache HTML+médias, WAF,            │
│         rate limiting, redirections, TLS                 │
├─────────────────────────────────────────────────────────┤
│  APP  : Next.js — RSC, ISR (articles), SSR (perso),     │
│         Server Actions (admin)                           │
├─────────────────────────────────────────────────────────┤
│  API  : Route Handlers /api/v1/* (public, cachée)       │
│         Server Actions (admin, authentifiées)            │
├─────────────────────────────────────────────────────────┤
│  JOBS : encodage vidéo, envoi e-mail, collecte SEO,     │
│         sitemaps, agrégation stats, backups              │
├─────────────────────────────────────────────────────────┤
│  DATA : PostgreSQL (+ replica lecture) · Redis ·        │
│         Meilisearch · S3/R2                              │
├─────────────────────────────────────────────────────────┤
│  TIERS: météo · vidéo · e-mail · données SEO ·          │
│         analytics · push · régie externe                 │
└─────────────────────────────────────────────────────────┘
```

## 02.3 Règle d'indépendance

Aucune dépendance propriétaire bloquante. Un export complet (dump PostgreSQL + archive des médias) doit être obtenable par une commande documentée : `pnpm run export:full`.

# 06. MODÈLE DE DONNÉES

## 06.1 Conventions

- Identifiants : **UUID v7** (triables chronologiquement). Colonne `id uuid primary key`.
- Horodatages : `timestamptz`, stockés en UTC. Colonnes `created_at`, `updated_at` sur toutes les tables.
- Suppression logique : `deleted_at timestamptz null` sur toutes les tables de contenu. Toute requête de lecture filtre `deleted_at IS NULL`.
- Nommage : `snake_case`, tables au pluriel.
- Contraintes d'intégrité référentielle **déclarées en base**, jamais uniquement applicatives.
- Index GIN sur les colonnes `jsonb` interrogées et sur la recherche plein texte.
- Partitionnement mensuel sur `ad_events`, `email_events`, `page_views`.

```sql
-- Trigger : maintien de search_vector (pondération A titre, B chapô, C corps)
CREATE FUNCTION articles_search_trigger() RETURNS trigger AS $$
BEGIN
  NEW.search_vector :=
    setweight(to_tsvector('french', unaccent(coalesce(NEW.title,''))), 'A') ||
    setweight(to_tsvector('french', unaccent(coalesce(NEW.kicker,''))), 'B') ||
    setweight(to_tsvector('french', unaccent(coalesce(NEW.lede,''))), 'B') ||
    setweight(to_tsvector('french', unaccent(coalesce(NEW.plain_text,''))), 'C');
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_articles_search BEFORE INSERT OR UPDATE ON articles
  FOR EACH ROW EXECUTE FUNCTION articles_search_trigger();
```

## 06.4 Format des blocs de contenu (`articles.body`)

Le corps est un **tableau JSON de blocs**. Jamais de HTML brut en base.

```ts
type Block =
  | { id: string; type: "paragraph"; text: RichText }
  | { id: string; type: "heading"; level: 2 | 3 | 4; text: string; anchor?: string }
  | { id: string; type: "list"; style: "bullet" | "number"; items: RichText[] }
  | { id: string; type: "quote"; text: string; author?: string; role?: string }
  | { id: string; type: "pullquote"; text: string; author?: string }
  | { id: string; type: "keypoints"; title?: string; items: string[] }   // "À retenir"
  | { id: string; type: "image"; mediaId: string; size: "inline"|"wide"|"full"; caption?: string }
  | { id: string; type: "gallery"; mediaIds: string[]; layout: "grid"|"carousel"|"mosaic" }
  | { id: string; type: "video"; mediaId?: string; provider?: "mux"|"youtube"; playbackId?: string; caption?: string; autoplayMuted?: boolean }
  | { id: string; type: "audio"; mediaId: string; title?: string }
  | { id: string; type: "table"; headers: string[]; rows: string[][]; caption?: string; source?: string }
  | { id: string; type: "embed"; provider: "x"|"facebook"|"instagram"|"youtube"|"tiktok"|"iframe"; url: string; html?: string }
  | { id: string; type: "chart"; chartType: "line"|"bar"|"pie"|"area"; data: unknown; source: string; updatedAt: string }
  | { id: string; type: "map"; lat: number; lng: number; zoom: number; markers?: unknown[] }
  | { id: string; type: "timeline"; events: { date: string; title: string; text?: string }[] }
  | { id: string; type: "beforeafter"; beforeMediaId: string; afterMediaId: string; labels?: [string,string] }
  | { id: string; type: "definition"; term: string; definition: string }
  | { id: string; type: "readmore"; articleIds: string[] }
  | { id: string; type: "qa"; question: string; answer: RichText }        // interviews
  | { id: string; type: "factcheck"; claim: string; verdict: "true"|"misleading"|"false"|"unverifiable"; explanation: string; sources: {label:string;url:string}[] }
  | { id: string; type: "divider" }
  | { id: string; type: "code"; language: string; code: string }
  | { id: string; type: "newsletter"; listKey: string }
  | { id: string; type: "ad"; slotCode: string };

// RichText : tableau de fragments avec marques
type RichText = { text: string; marks?: ("bold"|"italic"|"underline"|"strike"|"code"|"sup"|"sub")[]; link?: { href: string; external?: boolean } }[];
```

**Règles :**
- Chaque bloc porte un `id` stable (nanoid 10) servant d'ancre aux commentaires de relecture et au sommaire d'article.
- `plain_text` est régénéré à chaque enregistrement par concaténation des textes, et sert au comptage de mots, à la recherche et au calcul de densité de mots-clés.
- Les blocs `ad` sont insérés **automatiquement** au rendu (après le 3ᵉ et le 7ᵉ paragraphe) si aucun bloc `ad` manuel n'existe.

## 07.2 API d'administration

Préférer les **Server Actions** Next.js pour les formulaires du back-office, avec :
- vérification de session + permission **au début de chaque action**,
- validation Zod de l'entrée,
- écriture dans `audit_log`,
- invalidation de cache ciblée (`revalidateTag`).

Routes REST `/api/admin/*` uniquement pour : téléversement de médias, exports, webhooks, appels longue durée.

```ts
// Modèle obligatoire de toute Server Action
"use server";
export async function publishArticle(input: unknown) {
  const session = await requireSession();
  const data = publishArticleSchema.parse(input);
  await requirePermission(session, "article.publish", { categoryId: data.categoryId });

  const before = await repo.articles.findById(data.id);
  const after  = await services.articles.publish(data, session.user.id);

  await audit.log({ userId: session.user.id, action: "article.publish",
                    resourceType: "article", resourceId: data.id, before, after });

  revalidateTag(`article:${after.slug}`);
  revalidateTag(`category:${after.categoryId}`);
  revalidateTag("homepage");
  await search.index(after);
  return { ok: true, data: after };
}
```

- Mot de passe : 12 caractères minimum, vérifié contre une base de mots de passe compromis (API k-anonymat HIBP), haché en **Argon2id**.

- Journalisation : connexion, échec, changement de mot de passe, activation 2FA, changement de rôle.

# 10. ANIMATIONS ET INTERACTIONS

## 10.1 Grammaire

| Catégorie | Durée | Courbe | Exemples |
|---|---|---|---|
| Micro-interaction | 120–200 ms | `ease-out` | Soulignement qui se déploie, bouton enfoncé, icône de partage qui pivote, label flottant, coche tracée |
| Transition d'état | 200–320 ms | `--ease-signal` | Méga-menu, accordéon, bascule de thème en fondu croisé, suggestions de recherche |
| Entrée de contenu | 280–420 ms | `ease-out`, décalage 40 ms | Fondu + translation 12 px à l'entrée dans le viewport, cascade de grille |
| Macro-animation | 400–700 ms | ressort amorti | Transition d'image partagée vignette→article, menu mobile plein écran, entrée de long format |
| Boucle d'état | continue | linéaire | Pastille « direct », bandeau flash, squelettes |
| Lié au défilement | — | linéaire | Compactage du masthead, barre de progression, parallaxe **max 15 %** |

## 10.2 Règles strictes (bloquantes en revue de code)

1. **Seules `transform` et `opacity` sont animées.** Toute animation de `width`, `height`, `top`, `left`, `margin` ou `box-shadow` est refusée.
2. 60 fps visés, **plancher 50 fps** sur Android d'entrée de gamme.
3. **CLS < 0,1** : aucune animation ne provoque de décalage de mise en page.
4. `prefers-reduced-motion: reduce` → fondus de 100 ms uniquement, suppression des parallaxes, des défilements automatiques et des translations.
5. **Le contenu est peint d'abord, animé ensuite.** Aucun contenu au-dessus de la ligne de flottaison masqué en attente d'apparition au défilement.
6. Une animation d'entrée se déclenche **une seule fois** par élément et par session de page.
7. Maximum **3 animations simultanées** dans le viewport ; maximum 8 % du thread principal.
8. Toute animation > 5 s ou en boucle est interruptible par l'utilisateur.

## 10.3 Interactions à implémenter

- Masthead rétractable au défilement, transition fluide vers barre compacte.
- Transition d'image partagée entre carte et article (`layoutId` Framer Motion).
- Recherche en surcouche ouvrable au clavier (`/` ou `Ctrl+K`), fond assombri, résultats en cascade.
- Preview vidéo muette de 4 s au survol d'une vignette — **désactivée** si `navigator.connection.saveData` ou mode données réduites.
- Compteurs de vues et de mises à jour du direct avec incrémentation animée.
- Visionneuse plein écran : navigation clavier, gestes tactiles, zoom.
- Squelettes calqués sur la forme réelle du contenu — **jamais de spinner générique**.
- Retour haptique léger (`navigator.vibrate(10)`) sur partage et inscription, mobile uniquement.

# 12. MODULE SEO ET MOTEUR DE MOTS-CLÉS

## 12.1 Principe

Le SEO n'est pas une couche ajoutée en fin de projet : il est intégré au socle technique (§12.2), puis prolongé par un **moteur de suggestion de mots-clés** qui propose au journaliste, **avant publication**, les termes de courte et longue traîne les plus pertinents pour son sujet.

## 12.2 Socle technique obligatoire

| Domaine | Exigence |
|---|---|
| Rendu | RSC/ISR : le HTML servi contient le contenu intégral. **Aucune dépendance au JS pour l'indexation.** |
| Balises | Un seul `h1`, hiérarchie stricte, `<title>` ≤ 60 caractères, meta description 140–160, canonique systématique, `robots` par page |
| Données structurées | `NewsArticle`, `Article`, `VideoObject`, `LiveBlogPosting`, `ClaimReview`, `BreadcrumbList`, `Organization`, `Person`, `WebSite`+`SearchAction`, `FAQPage` — générées automatiquement et **validées dans les tests** |
| Sitemaps | Index segmenté : `sitemap-articles-{n}.xml` (50 000 URL max), `sitemap-categories`, `sitemap-tags`, `sitemap-authors`, `sitemap-videos`, `sitemap-images`. **`sitemap-news.xml` limité aux 48 dernières heures.** Régénération à chaque publication + ping IndexNow |
| Flux | RSS **et** Atom par rubrique, mot-clé, auteur, dossier ; MRSS pour les vidéos |
| International | `hreflang` réciproques entre versions linguistiques + `x-default`, URL localisées |
| Partage | Open Graph et Twitter Cards complets ; image sociale **générée automatiquement** (`opengraph-image.tsx`) si absente |
| Google News / Discover | Pages auteur, transparence éditoriale, politique de corrections publiée, images ≥ 1200 px de large |
| Hygiène | 404 et 410 corrects, 301 permanentes, **aucune chaîne de redirection**, pagination indexable, contrôle du contenu dupliqué et de la cannibalisation |

### Exemple de JSON-LD `NewsArticle` à générer

```json
  "@type": "NewsArticle",
  "headline": "{title, ≤110 car.}",
  "description": "{lede}",

  "dateModified": "{updated_content_at ISO8601}",
  "articleSection": "{category.name}",

  "image": [ "{cover 16:9 ≥1200px}", "{cover 4:3}", "{cover 1:1}" ],
```

## 12.3 Moteur de suggestion — architecture

Service dans `lib/seo/keyword-engine/`. Invoqué depuis l'éditeur via Server Action `suggestKeywords(input)`.

### Pipeline en 9 étapes

```
1. SAISIE
   Entrée : { topic?: string, articleId?: string, draftText?: string,
              locale: "fr", country: "GN", categoryId?: string }

2. EXTRACTION SÉMANTIQUE
   → entités nommées, thème principal, zone géographique, période,
     intention dominante (informational | news | transactional | navigational)
   → via LLM + règles ; sortie normalisée

3. EXPANSION — génération large de candidats
   a) autocomplétion : requêtes seed × [a–z] × préfixes interrogatifs
      (comment, pourquoi, qui, quand, combien, où, quel, est-ce que)
   b) recherches associées et "autres questions posées"
   c) variantes morphologiques, singulier/pluriel, synonymes
   d) traductions et translittérations (noms propres guinéens)
   e) formulations locales (dictionnaire interne, voir 12.5)
   f) expansion LLM sur le thème
   → 200 à 800 candidats bruts

4. ENRICHISSEMENT
   Pour chaque candidat : volume, tendance, difficulté, saisonnalité, CPC
   Sources par ordre de priorité : GSC > autocomplete > Trends > provider payant
   → mise en cache 30 jours dans keyword_metrics ; ne jamais réinterroger
     un terme déjà collecté récemment (maîtrise du coût)

5. ANALYSE SERP (sur les 10 meilleurs candidats seulement)
   → type de contenu dominant, longueur moyenne, structure,
     présence de blocs enrichis, concurrents présents

6. CLUSTERING
   → embeddings des candidats, regroupement par similarité cosinus (seuil 0,82)
   → un cluster = une intention = un article
   → confrontation aux clusters déjà couverts par le site

7. SCORING
   opportunity =
       (volume_weighted ^ 0.5)
     * trend_factor          // spiking 1.6 | rising 1.3 | stable 1.0
                             // seasonal 1.1 si en saison | declining 0.7
     * affinity_factor       // 1.0 à 1.5 selon l'autorité du site sur le cluster
     / (1 + difficulty / 100)
   Les coefficients sont stockés dans settings.seo.scoring et modifiables
   par un administrateur SANS redéploiement.

8. RESTITUTION
   {
     focusKeyword:     { term, volume, difficulty, score, rationale },
     secondary:        Keyword[],   // 3 à 6, moyenne traîne
     longTail:         Keyword[],   // 8 à 15
     questions:        string[],    // à traiter en intertitres
     titles:           string[],    // 3 propositions ≤ 60 car.
     metaDescriptions: string[],    // 3 propositions 140-160 car.
     outline:          { heading: string; keywords: string[] }[],
     internalLinks:    { articleId, title, suggestedAnchor }[],
     cannibalization:  { articleId, title, sharedIntent, recommendation }[],
     cluster:          { id, label, coverage }
   }

9. CONTRÔLE AVANT PUBLICATION
   → recalcul du score SEO à chaque frappe (debounce 1500 ms)
   → checklist affichée ; blocage doux si critères majeurs manquants
```

**Architecture d'adaptateur obligatoire :**
```ts
interface KeywordProvider {
```

Changer de fournisseur ne doit demander **aucune** réécriture hors du dossier `providers/`. Un provider `none` doit exister, fonctionnant uniquement sur GSC + autocomplete + LLM.

## 12.5 Spécificité guinéenne — exigence forte

Les données de volume de recherche sont **notoirement pauvres pour la Guinée**. Le moteur doit donc :

1. **Pondérer les volumes** par un coefficient régional paramétrable (`settings.seo.region_weight`, défaut : ×3,5 pour une requête francophone ouest-africaine par rapport au volume mondial affiché).
2. **Privilégier GSC et l'autocomplétion**, qui reflètent la réalité locale, plutôt que les estimations des outils commerciaux.
3. Maintenir un **dictionnaire local** (`lib/seo/dictionaries/gn.ts`) : patronymes guinéens et leurs graphies alternatives (Condé/Conde, Diallo, Camara, Bah/Ba, Sylla, Touré/Toure), toponymes (Conakry, Kankan, N'Zérékoré/Nzerekore, Labé/Labe, Kindia, Boké/Boke, Siguiri), sigles institutionnels (CNRD, CENI, RTG, BCRG, SMB, CBG, ANSS), et les variantes sans accents et sans apostrophes.
4. **Ne jamais présenter une absence de données comme une absence d'intérêt.** Quand aucun volume n'est disponible, afficher « volume non mesuré » et se reposer sur la fraîcheur et l'affinité.

### Autres fonctions du panneau

- **3 propositions de titres** et **3 meta descriptions**, avec aperçu du rendu dans les résultats Google **et** dans un partage social.

## 13.2 Algorithme de sélection (`lib/ads/serve.ts`)

```
Entrée : slotCode, contexte { path, categoryId, tags[], format, country,
                              city, device, locale, hour, weekday,
                              visitorType, visitorHash, isSensitive }

1. Filtrer ad_slots : code actif
2. Récupérer les créations éligibles :
   - campagne status='running' ET now() ENTRE starts_at ET ends_at
   - creative.slot_code = slotCode ET is_active
3. Appliquer le ciblage (targeting JSONB) :
   catégories, tags, formats, pays, villes, devices, langues,
   heures, jours, type de visiteur
4. EXCLUSIONS OBLIGATOIRES :
   - si contexte.isSensitive (deuil, catastrophe, fait divers grave,
     détecté par settings.ads.sensitive_keywords) → ne rien servir
   - exclusion concurrentielle : pas deux annonceurs du même `sector`
     sur la même page
   - article.is_sponsored → AUCUNE publicité tierce dans cet article
5. Plafonnement : compteur Redis `cap:{campaignId}:{visitorHash}:{yyyymmdd}`
   → écarter si >= frequency_cap
6. Trier par priority ASC, puis tirage aléatoire pondéré par `weight`
7. Si aucune création → servir AD-19 (auto-promotion)
8. Journaliser l'impression de façon asynchrone (POST /api/v1/ads/event)
```

## 13.3 Règles de qualité (bloquantes)

- **Espace réservé en CSS avant chargement** : aucun format ne provoque de décalage (CLS = 0 sur les emplacements).
- Chargement différé de tous les emplacements sous la ligne de flottaison (`IntersectionObserver`, marge 200 px).
- Rafraîchissement possible toutes les 30 s pour les formats collants, **maximum 5 rafraîchissements**.
- **Aucun format sonore en lecture automatique. Aucun interstitiel avant le premier affichage du contenu. Aucun format masquant le contenu sur mobile hors bandeau fermable.**
- Poids maximum : 150 Ko (image), 2 Mo (HTML5). Contrôlé à l'upload.
- Contenus sponsorisés visuellement distincts et **explicitement étiquetés**.
- Détection de bloqueur de publicité → message courtois, **non bloquant**.
- `ads.txt` et `sellers.json` publiés et maintenus (`/ads.txt` servi depuis `settings`).

# 17. SÉCURITÉ ET CONFORMITÉ

## 17.1 Sécurité applicative

- HTTPS strict + HSTS (`max-age=63072000; includeSubDomains; preload`).
- En-têtes : CSP restrictive (nonce sur les scripts en ligne), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `X-Frame-Options: SAMEORIGIN`.
- Contrôle d'accès **vérifié côté serveur pour chaque opération**.
- Requêtes paramétrées exclusivement (ORM). Assainissement des contenus HTML riches (blocs `embed`) via liste blanche.
- Rate limiting Redis : authentification (5/15 min), formulaires (3/min), recherche (30/min), API publique (120/min).
- Turnstile invisible sur tous les formulaires publics.
- Téléversements : vérification du type **réel** (magic bytes), taille max, analyse antivirus, stockage hors du domaine applicatif, noms assainis, **suppression des EXIF GPS**.
- Journalisation des accès et actions sensibles, conservation 12 mois, alertes sur comportement anormal.
- Mises à jour de sécurité des dépendances **mensuelles**, analyse automatisée (`pnpm audit`, Dependabot).
- **Test d'intrusion externe avant mise en production.** Correction obligatoire des vulnérabilités critiques et élevées avant lancement.

## 17.2 Sauvegardes et continuité

| Élément | Politique |
|---|---|
| Base — PITR | Restauration à un instant donné sur **30 jours** |
| Base — instantané quotidien | Conservation 90 jours |
| Base — copie mensuelle | Conservation 12 mois, **région distincte** |
| Médias | Versionnage + verrouillage contre la suppression |
| RPO | ≤ 15 minutes |
| RTO | ≤ 2 heures |
| Test de restauration | **Complet et documenté, 2×/an minimum** |

Page d'état publique (`status.infospro.net`) et procédure d'incident écrite avec niveaux de gravité et chaîne d'escalade.

## 17.3 Données personnelles

- RGPD (visiteurs européens) + législation guinéenne sur la cybersécurité et la protection des données. Point de contact responsable désigné.
- **Bandeau de consentement conforme** : refus aussi simple que l'acceptation, granularité par finalité (mesure d'audience, publicité, personnalisation), **aucun traceur non essentiel avant consentement**, consentement révocable et horodaté.
- Registre des traitements, durées de conservation par catégorie, minimisation.
- Droits des personnes outillés dans le back-office : recherche d'un abonné, export, anonymisation, effacement.
- Contrats de sous-traitance, cartographie des transferts, chiffrement au repos et en transit.
- Procédure de notification de violation sous **72 h**.
- **IP jamais stockée en clair** : uniquement hachée avec sel (`ip_hash`).

- Mentions légales complètes : éditeur, directeur de publication, hébergeur, numéro d'enregistrement auprès de l'autorité de régulation.
- Procédure de droit de réponse et de correction accessible **depuis chaque article**.

# 25. GLOSSAIRE

| Terme | Définition |
|---|---|
| **Serverless** | Exécution de code sans serveur à administrer, facturée à l'usage, mise à l'échelle automatique |
| **RSC** | React Server Components — composants rendus sur le serveur, n'envoyant pas leur JS au navigateur |
| **ISR** | Incremental Static Regeneration — page pré-générée puis rafraîchie automatiquement |
| **LCP / INP / CLS** | Core Web Vitals : vitesse d'affichage du contenu principal / réactivité / stabilité visuelle |
| **Courte traîne** | Requête courte (1–2 mots), volume élevé, forte concurrence |
| **Longue traîne** | Requête longue (≥ 5 mots), volume faible mais nombreuse et peu concurrentielle |
| **Cannibalisation** | Plusieurs pages d'un même site se concurrençant sur la même intention de recherche |
| **Clustering sémantique** | Regroupement de mots-clés par proximité de sens — un cluster = un article |
| **GEO / AEO** | Optimisation pour les moteurs génératifs et les réponses d'IA |
| **Double opt-in** | Inscription confirmée par un clic dans un e-mail de validation |
| **Above the fold** | Partie visible sans défilement — zone d'attention maximale |
| **Native ad** | Publicité adoptant l'apparence du contenu éditorial, obligatoirement signalée |
| **Capping** | Plafonnement du nombre d'affichages d'une publicité par visiteur et par période |
| **Dateline** | Mention de lieu en tête d'article (« Conakry, envoyé spécial ») |
| **Chapô** | Paragraphe de résumé placé sous le titre |
| **Surtitre (kicker)** | Courte mention au-dessus du titre, souvent la rubrique |
| **Live blog** | Couverture d'un événement en fil d'entrées horodatées actualisées en direct |
| **PITR** | Point-In-Time Recovery — restauration de la base à un instant précis |
| **RPO / RTO** | Perte de données maximale acceptée / durée maximale d'interruption acceptée |
